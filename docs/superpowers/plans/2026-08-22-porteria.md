# La Pantalla de Portería — Plan de Implementación

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Que la pantalla de ingreso reconozca a los estudiantes que escanea, en vez de decir "carnet no reconocido" a los 1.200 cada mañana.

**Architecture:** El servidor ya devuelve el nombre de cada estudiante registrado, y la pantalla lo descarta. Se usa esa respuesta como fuente principal del nombre, con la copia local como respaldo sin conexión, y se distingue de verdad un carnet desconocido de uno que simplemente no está en la copia local.

**Tech Stack:** React 18, TypeScript, Vitest.

**Spec:** Verificación del 22 de agosto de 2026 contra la base de carga, registrada en la sección 6.l de `docs/INFORME-FINAL.md`.

## El defecto, medido

La pantalla de ingreso busca al estudiante en la base **local del dispositivo**:

```ts
const estudiante = await db.students.where('documentId').equals(carnet.documentId).first();
if (!estudiante) setUltimo(`Carnet ${carnet.documentId} no reconocido`);
```

Pero esa copia local viene de `GET /api/sync/bootstrap`, que devuelve **solo los
estudiantes de los cursos que dicta quien entró**. Medido con el usuario de coordinación,
que es quien está en la portería:

```
bootstrap de coordinacion:  bloques: 0 | estudiantes: 0 | dias: 88
```

Cero estudiantes. La pantalla dirá **"Carnet no reconocido" a los 1.200**, uno por uno.
El registro se guarda igual —eso funciona—, pero quien está en la puerta ve un mensaje de
error constante y **pierde la capacidad de detectar un carnet realmente malo**, que es
justo para lo que sirve ese mensaje.

Lo irónico es que la información está ahí. El servidor responde:

```json
{"accepted":1,"rejected":[],"names":{"aaaa-...-0009":"NOMBRE500 SEGUNDO500 APELLIDO500 SEGUNDOAP500"}}
```

Y la pantalla **declara el tipo de la respuesta sin `names`**, de modo que el nombre se
descarta al deserializar.

**Los tres estados que hay que distinguir**, y que hoy se confunden en uno:

| Situación | Qué se muestra hoy | Qué debe mostrarse |
|---|---|---|
| El servidor confirma y da el nombre | "Carnet X no reconocido" | El nombre del estudiante |
| El servidor rechaza el carnet | "Carnet X no reconocido" | "Carnet X no registrado" y en rojo |

El tercero es el que más importa para la portería: **el ingreso queda guardado igual**, y

- [ ] **Step 3: Recoger el nombre en `enviar()`**

En `Ingreso.tsx`, ampliar el tipo de la respuesta y devolver lo que hace falta:

```tsx
  /**
   * Envia la cola y devuelve lo que el servidor dijo de cada ingreso.
   * El servidor resuelve el nombre aunque el dispositivo no tenga a ese estudiante en
   * su copia local, que es el caso normal en la porteria: quien esta ahi no dicta
   * cursos, asi que su copia local esta vacia.
   */
  async function enviar(): Promise<{
    nombres: Record<string, string>;
    rechazos: Record<string, string>;
    alcanzable: boolean;
  }> {
    const cola = await db.entryOutbox.toArray();
    setPendientes(cola.length);
    if (cola.length === 0) return { nombres: {}, rechazos: {}, alcanzable: true };

    try {
      const res = await api.post<{
        accepted: number;
        rejected: { id: string; reason: string }[];
        names: Record<string, string>;
      }>('/api/entry/sync', { entries: cola.map(({ name, error, ...e }) => e) });

      const rechazos: Record<string, string> = {};
      for (const r of res.rejected) rechazos[r.id] = r.reason;

      for (const e of cola) {
        if (rechazos[e.id]) await db.entryOutbox.update(e.id, { error: rechazos[e.id] });
        else await db.entryOutbox.delete(e.id);
      }
      setPendientes(await db.entryOutbox.count());
      return { nombres: res.names ?? {}, rechazos, alcanzable: true };
    } catch (e) {
      if (!(e instanceof OfflineError)) throw e;
      return { nombres: {}, rechazos: {}, alcanzable: false };
    }
  }
```

- [ ] **Step 4: Decir lo que corresponde en `registrar()`**

```tsx
  async function registrar(documentId: string) {
    setError('');
    const id = crypto.randomUUID();
    await db.entryOutbox.put({ id, documentId, scannedAt: new Date().toISOString() });

    const { nombres, rechazos, alcanzable } = await enviar();

    if (rechazos[id]) {
      setUltimo('');
      setError(`Carnet ${documentId} no registrado. Revise el carnet del estudiante.`);
      return;
    }
    if (nombres[id]) {
      setUltimo(nombres[id]);          // el servidor confirmo y dio el nombre
      return;
    }
    if (!alcanzable) {
      // Sin conexion: el ingreso queda guardado. Decir "no reconocido" haria que lo
      // escanearan tres veces pensando que fallo.
      const local = await db.students.where('documentId').equals(documentId).first();
      setUltimo(local
        ? local.fullName
        : `Carnet ${documentId} registrado, se verificara al sincronizar`);
      return;
    }
    setUltimo(`Carnet ${documentId} registrado`);
  }
```

## Fuera de alcance

1. **Descargar los 1.200 estudiantes al dispositivo de portería.** Serían unos 100 KB y
   habría que decidir quién los recibe y cuándo se refrescan. El servidor ya resuelve el
   nombre, así que solo haría falta para funcionar sin conexión en la puerta, y la
   portería del colegio tiene la mejor conexión del edificio: es donde está el router.
2. **Agrupar los escaneos en un solo envío.** Cada escaneo manda la cola entera, que
   normalmente es un ingreso. Con conexión mala la cola crece y se envía junta sola. Un
   agrupador explícito optimizaría algo que ya se comporta bien.
3. **Foto del estudiante al escanear.** Sería la confirmación visual más útil para quien
   está en la puerta, pero necesita almacenamiento de imágenes y política de datos de
   menores: su propio plan.
4. **Avisar de la llegada tarde en el momento del escaneo.** Requiere que el colegio
   defina desde qué hora se considera tardanza, que sigue pendiente.

## Riesgos

| Riesgo | Impacto | Mitigación |
|---|---|---|
| Cada escaneo espera la respuesta del servidor | Con conexión lenta, la puerta se atasca | El registro se encola **antes** de enviar; si tarda, el ingreso ya está guardado y el mensaje llega cuando llegue |
| El nombre viene del servidor y no de la copia local | Sin conexión no hay nombre | Se cae a la copia local y, si tampoco está, se dice que quedó registrado, que es lo cierto |
| Mostrar el nombre completo en la puerta | Dato de un menor visible en pantalla | Es la misma información que ya lleva impresa el carnet que se acaba de escanear |

**Cobertura.** El defecto tiene tarea (Task 1) y queda como invariante (Task 2). Se

**Sin marcadores de posición.** Cada paso trae el código o el comando exacto.

**Consistencia.** `enviar()` devuelve `{nombres, rechazos, alcanzable}` y `registrar()`
consume esas tres claves. El tipo de la respuesta incluye ahora `names`, que es como lo
llama `EntryController.EntryResult`. `OfflineError` es la que ya lanza `api` en
`client.ts`.

**Lo que este defecto enseña.** El dato correcto estaba llegando en la respuesta desde el
primer día. Se perdía en una línea de tipos: al declarar la forma de la respuesta sin
`names`, el campo se descartaba silenciosamente. **TypeScript describe lo que esperas, no
lo que llega**, y una declaración incompleta no da ningún error: simplemente hace
invisible lo que sobra.
